# PROJECT AUR BHAI - MASTER ECOSYSTEM MANIFEST & KNOWLEDGE TRANSFER
**Document State:** FROZEN (Arch v3.10 | Eng v2.8)

## 1. PRODUCT CONCEPT & ULTIMATE VISION
**The Concept:** Project Aur Bhai is a decentralized, voice-orchestrated **Mobile Agentic OS** and local **Edge Server** acting as a proxy for human activity. It is completely use-case agnostic. It natively runs as a secure, headless execution environment managing hardware sensors, acoustic handshakes, and an AI-driven Model Context Protocol (MCP). All features are dynamically added via local, sandboxed "Plugins."

**The Vision:** To pioneer a decentralized, zero-marginal-cost software ecosystem where:
1. **Software Generates Itself:** Users can orally prompt their device to write, compile, and iteratively refine its own tools on the fly — through one-shot commands or guided, back-and-forth conversation (§2.8).
2. **Infrastructure Costs are Zero:** Through a Bring-Your-Own-Key (BYOK) paradigm, platform API liabilities and costs are completely shifted to the user.
3. **Data is Sovereign (Alternative 3 Core):** The user is the sole owner of all data generated by the app — sensor telemetry, coordinates, labeled packs, and vault assets — and that data has personal and monetary value. By default, all datasets reside in an encrypted on-device vault; machine learning **inference** runs 100% offline on-device. Users may **train** tiny models on-phone or authorize Path C laptop/GPU training (§2.2, §2.9). Data may leave the device **only** through an explicit, user-authorized connection (self-use train/export, free sharing, or sale of labeled packs). The platform never initiates silent or background egress. See §2.6.
4. **Local Edge Server & Dashboards:** The device runs a background HTTP/WebSocket server enabling Agents to host real-time, high-fidelity HTML5 dashboards directly from `localhost` (accessible locally via mobile Chrome or other devices on the same Wi-Fi) without sending telemetry to the cloud.

## 2. ARCHITECTURAL PARADIGMS (Arch v3.10 Frozen)

### 2.1 The 4-Tier Security & Execution Matrix
*See §2.7 for the agent verification lifecycle and marketplace promotion rules.*
* **[Class 1] CORE (Native Shell):** Unrestricted hardware access (microphone, GPS, coarse + fine telemetry buffers, Model Studio self-use train/import, compressed candidate store).
* **[Class 2] VERIFIED (Local Native / Sandboxed):** Pre-vetted code or user-approved local agents. Granted background execution; may call `System.runModel` / `System.runONNX` on bound vault models.
* **[Class 3] UNDER DUE DILIGENCE:** Unvetted scripts. Restricted to Delegated Scoping (User must explicitly say "Ask [Agent] to..."). Completely deaf to general voice activity.
* **[Class 4] NOT YET VERIFIED:** Untrusted scripts. Zero real-world sensor access. Runs via simulated data replays.

### 2.2 Alternative 3: Sovereign Data & Dual-Locus ML (Arch v3.9)
Data sovereignty with a non–data-scientist Path L on-ramp — laptop Python is no longer the only training story:

1. **Local storage lanes:** Coarse telemetry (dashboards / long history) in encrypted on-device SQLite. Fine event windows and label candidates in a **compressed artifact lane** (ring buffer in RAM → write-compressed snapshots). Uncompressed fine history is an Arch defect.
2. **Path H then Path L:** Sensor Bro Code always ships a usable **heuristic** (Path H) from the coding LLM. An optional **learned** binding (Path L) matures via ambient capture → semi-auto labels → train → bind → test (§2.9). Heuristic remains the runtime default until model maturity is `trusted` (or the user forces “try learned”).
3. **Dual-locus training:** **Phone** — tiny / constrained models only, battery- and thermal-aware (optional charge/idle train). **Laptop / GPU (Path C)** — heavier training on user-authorized export of labeled packs; weights/ONNX return to the vault. Inference always on-device.
4. **Native offline inference:** Bound models run 100% offline via the JS bridge (`System.runModel` / `System.runONNX`). IMPROVE must not silently replace a bound model with new magic thresholds without user consent.
5. **Labels as assets:** Labeled packs stay sovereign by default; later sale/license is explicit egress under §2.6 and `[MS-DATA-MARKET]` — never silent pooling.

### 2.3 Audio-Direct LLM Paradigm & Custom Handshake
Moving beyond the limitations of native OS dictation (Speech-to-Text), which actively interferes with background listening:
1. **Raw Audio Pipeline:** The device captures raw audio commands directly from the microphone using pure native audio recording and passes the audio file directly to the user's BYOK LLM API. The problematic `speech_to_text` OS integration has been completely removed to prevent OS-level Voice Assistant hijacking.
2. **LLM Voice Generation (TTS):** The system generates the Handshake response ("Haan Bhai") via LLM-powered Text-to-Speech APIs (e.g. OpenAI TTS) to ensure perfect dialects (Male/Female options), completely bypassing robotic OS default voices.
3. **User-Trained Voice Studio (Deferred to Milestone 7):** Custom Wake Word recording and offline neural network training (Porcupine) are shifted to a later milestone to prioritize core responsiveness.
4. **Intuitive Tap Gestures:** The mic interaction is designed around familiar voice-note behaviors:
    *   **Single Tap (Idle):** Wakes the system, plays handshake response, begins recording.
    *   **Single Tap (Recording):** Ends the recording early and immediately processes the command.
    *   **Double Tap (Recording):** Cancels the recording, deletes the audio, and silently returns to idle.

### 2.4 Bro Code (Bhai log) & Internal Agents
User-generated codebases are **Bro Code** (collectively **Bhai log**). The word **Agent** is reserved for internal AI workers that build and verify them (Coder, Tester, Deployer).

Bro Code classifications (formerly "Agents"):
1. **Action Bro Code:** Utility commands on request (e.g. Calculator).
2. **Telemetry Bro Code:** Background sensor monitors writing to SQLite.
3. **Server/Dashboard Bro Code:** Local edge HTML5 dashboards.
4. **Orchestrator Bro Code:** Chains other Bro Code units (deferred).

**Model binding metadata (Arch v3.9):** Every Bro Code may declare ML fields (illustrative names): `usesModel`, `modelRef` → vault `model:<name>`, `heuristicFallback`, `datasets[]`, `labelSchema`, `triggerHints`, `capturePolicy`, `splitPolicy`, `maturity`. Runtime prefers the bound model when maturity is `trusted` (or user forces learned mode); otherwise Path H. See §2.9.

**Author / refine pipeline:** Coder Agent emits full `scriptBase64` rewrites (surgical Base64 patches are last-resort). Tester Agent runs smoke tests in an **in-memory sandbox vault** so C4 Bro Code never touches sovereign data until promoted to C2.

### 2.5 The JS Bridge Paradigm & Caching (Arch v3.9)
To prevent recompiling Dart and allow dynamic Bro Code generation:
1. **Headless Javascript Sandbox:** We embed QuickJS natively in Flutter. The LLM writes lightweight, dynamic JS scripts on the fly, which run locally on the phone's CPU.
2. **The Sovereign Bridge:** The Flutter app exposes strict native boundaries: `System.querySQL(query)`, `System.sendHTTP(url, payload)`, `System.runModel(modelRef, input)` / `System.runONNX(model, input)`, and `System.mountRoute(path, html)`.
3. **Native ML Pipeline:** Training is dual-locus (§2.2): tiny on-phone trainers and/or user-authorized laptop/GPU Path C. Bound model artifacts live in the vault and execute offline via the bridge. Codec choice (ONNX Runtime vs TFLite, etc.) is an Eng decision inside `[MS-MODEL-RUNTIME]`.

### 2.6 Data Sovereignty and User-Controlled Egress (Arch v3.9)
The user is the **sole owner** of all data generated by the app. That data has personal and monetary value. Sovereignty means **ownership and control**, not absolute isolation.

1. **Default Residence:** All telemetry, compressed fine candidates, labeled packs, vault assets, and Bro Code outputs reside on-device unless the user explicitly authorizes otherwise.
2. **User-Authorized Egress:** The user may set up or accept a connection to transfer data off-device. Every egress event requires explicit, per-connection (or per-pack) user authorization. Egress modes include:
    * **Self-use (Path C / Model Studio):** Export *labeled* (or explicitly selected) packs to a laptop for training and import weights/ONNX back — Class 1 Model Studio flows, user-visible.
    * **Free sharing:** User voluntarily shares data with another party at no cost.
    * **Sale / monetization:** User sells or licenses **labeled packs** (windows + labels + provenance) via user-authorized transfer protocols (future `[MS-DATA-MARKET]`). Self-use train ≠ marketplace listing; separate consent.
    * **Bro Code Commons publish (Arch v3.10):** User-authorized egress of **authored Bro Code** (source + schema + license metadata) to the shared commons registry (§2.10 / `[MS-BROCODE-COMMONS]`). Distinct from labeled-pack sale. Bound Path L models and sovereign telemetry / labeled packs are **not** included unless the author explicitly attaches them with separate consent.
3. **Prohibited Egress:** Silent egress, background egress, and platform-initiated egress are forbidden. The OS must **not** ship a casual built-in “dump all my raw telemetry” button for arbitrary export — that remains agent-authored via the sovereign bridge where appropriate. **Exceptions (Class 1, explicit, visible):** Model Studio self-use train/export/import, later Data Market pack listing, and user-initiated Bro Code Commons publish. Ambient Path L **collection** stays on-device; it is not egress.
4. **Secure Vault:** The encrypted local vault is the trust boundary. Connections that read from or write to the vault must be user-visible and user-approved.

### 2.7 Agent Verification Lifecycle and Marketplace (Arch v3.5; Commons licenses v3.10)
Every Bro Code unit — whether self-authored (voice or UI) or picked up from the ecosystem — must pass through a verification state machine before gaining real sensor access. This ties directly to the 4-Tier Security Matrix (§2.1).

**State machine:**
```
Not Verified (C4)  →  Due Diligence (C3)  →  Verified (C2)
```

1. **Entry — Not Verified (C4):** Every newly created or marketplace-picked Bro Code starts here. **RUN is disabled** in UI and engine until promotion to Verified (C2). Voice/UI authoring creates and registers at C4 after explicit BUILD approval, but does not execute until the user promotes. Zero real-world sensor access until C2.
2. **Agent Marketplace (Bro Code listings):** The Not Verified (C4) pool doubles as the **Agent Marketplace** — a browsable catalog of community or third-party **Bro Code** units. Picked-up Bro Code enters at C4. Near-term local shell: `[MS-USER-ECOSYSTEM-UX3]` / `[MS-USER-ECOSYSTEM-AGT2]`. Full publish / license / re-share commons: §2.10 / `[MS-BROCODE-COMMONS]`.
3. **Due Diligence (C3):** When the user requests promotion, the Bro Code undergoes an automated and/or assisted **malicious-intent check** against the user (data exfiltration patterns, credential harvesting, destructive SQL, etc.). C3 units are restricted to delegated scoping — the user must explicitly invoke them ("Ask [Agent] to..."). **RUN remains disabled** until C2.
    * **Important:** Due diligence is **static policy / malicious-intent scanning** of source text. It does **not** execute the Bro Code. Syntax and runtime errors come from QuickJS `validateScriptSyntax` / RUN. IMPROVE **verify-before-handoff** gates on QuickJS syntax before offering APPLY. A SyntaxError on last RUN and a due-diligence finding can appear together because they are independent checks.
4. **Verified (C2):** Bro Code that passes due diligence (or is force-promoted with device authentication) gains **RUN enabled**, real sensor access, and background execution privileges. The JS bridge refuses execution for non-C1/C2 units as defense in depth.
5. **Self-Authored + Flagged Path:** If a user self-authors Bro Code that the due-diligence check flags as potentially harmful to the user (self-harm scenario), the system:
    * Displays a **reconsideration warning** listing the specific reasons.
    * If the user insists on proceeding, requires a **device screen lock / biometric gate** (`FlutterFragmentActivity` + `local_auth`) to force-promote to Verified (C2).
6. **Promotion Gate:** No Bro Code may advance from C4 → C3 → C2 without passing (or explicitly overriding) the due-diligence check. **IMPROVE** is the path to fix flagged scripts (syntax errors, false-positive DOM flags in dashboard HTML, bad outputs) before promotion. See `[MS-DUE-DILIGENCE]` for scan hardening (false-positive HTML stripping, finding codes, UX that separates syntax vs policy).
7. **Commons license + revision (Arch v3.10):** Marketplace / commons listings carry `license`, `revisionId`, and optional `parentRevisionId` (§2.10). Re-share after modify creates a **new revision** under the license conflict rules; paid acquisition does **not** skip C4 entry or due diligence.

### 2.8 Single-Call Elicitation Protocol & Conversational Agent Authoring (Arch v3.7; Path L slots v3.9)
The Core is a verb-first intent dispatcher with multi-turn conversational state. **Every user turn uses exactly one LLM call** — audio/text + fat App Spec template in, merged spec + spoken confirmation out. No chained extract/paraphrase/classify calls on the hot path.

1. **Core Intent Classification (fused in single parseTurn):** The LLM classifies intent in the same call that fills the spec template. The Core routes on the returned object and never string-matches ASR text:
    * **EXECUTE** ("Ask <agent> to...") — invoke an existing agent.
    * **FEED** ("Tell <agent> that...") — push runtime data into an agent's inbox.
    * **AUTHOR** ("Build / Make / Get me / I want … an agent/app/tool/dashboard") — open authoring elicitation. A deterministic author-verb safety net reclassifies mislabeled DIRECT turns.
    * **REFINE** ("Fix / Improve / Update <agent>") — open refinement on an existing agent (voice or in-UI Improve).
    * **DIRECT** — conversational reply or capability Q&A.
2. **App Spec Slot State Machine:** Authoring walks conditional slots in sequence. Each slot: `empty → proposed → confirmed`. Confirmation is by explicit agreement **or** implicit consent (user does not object on the next turn). Objection re-opens the slot. Conditional slots (triggers, sensors, external keys, edge cases, external integrations) enter the queue only when earlier answers make them relevant.
3. **AUTHOR slot sequence:** purpose → name (LLM suggests) → invocation prompt → parameters (parsed from invocation → inputSchema) → behavior + suggested response → data sources → outputs → [?] triggers beyond voice → [?] sensors/permissions → [?] external BYOK keys → example/success → [?] edge cases → [?] external integrations (X/FB/Instagram/YouTube/Threads/webhook via `System.sendHTTP`, user-authorized egress §2.6, C2 gate §2.7) → [?] **learned path** (`usesModel`, `datasets[]`, `labelSchema`, `triggerHints`, `capturePolicy` / fine-window length, `splitPolicy`, train locus phone vs laptop) when purpose+sensors imply noisy event classification.
4. **Concise per-turn echo:** The Core speaks only the slot(s) just captured plus the next question — it does **not** re-read the entire spec every turn. A live **visual authoring panel** (numbered checklist, tap-to-edit) mirrors progress and provides question indexing.
5. **Mandatory final BUILD gate:** When all relevant slots are confirmed, the session enters **review** and speaks the full recap once. Nothing is written to the vault until the user taps **Build** or says "build it". Due diligence runs at build time and is surfaced on screen + voice before/with registration at C4.
6. **English only (v3.7):** All spoken prompts and confirmations are English until multilingual is re-enabled.
7. **Refinement Loop:** "Fix <agent>" (voice) or **Improve** (Agents page) loads vault source, gathers change, proposes patch, applies on confirm, re-registers at C4 on material change per §2.7. Bound models are not silently discarded for new hardcoded thresholds.
8. **Core Agents as JS Vault Agents:** Calculator, DrivingCoach remain refinable JS vault agents; native Dart reserved for Class 1 hardware shells.
9. **Path H / Path L authoring fork (Arch v3.9):** When the ask smells like continuous noisy sensor classification (e.g. pothole detection), the Coder always emits a working Path H Bro Code; Path L is opt-in with ambient capture expectations (e.g. ~30–60s fine windows) and proposed `labelSchema`, `datasets`, `triggerHints`, and `splitPolicy`. Prefer qualitative severity labels over fake physical depth/breadth unless the user insists. Standard label-template libraries are deferred.

### 2.9 Model Studio & Ambient Path L Loop (Arch v3.9)
Class 1 platform capability so non–data-scientists can grow a model while living with heuristics. Pixel-perfect UX is milestone work; **states and rules** are frozen here.

1. **Coarse vs fine telemetry:** Coarse stream (~multi-second samples) feeds dashboards and long history. **Fine ring buffer** (user-tunable high-rate window) feeds event detection and Path L candidates. Without fine capture, Path L is fantasy.
2. **Compression (non-negotiable):** Fine/candidate windows are **compressed at write time** (or immediately on window close). Bound RAM via ring buffer; only selected windows serialize. Retention caps + LRU/evict for stale unlabeled candidates; labeled packs persist until user delete/export. Studio/train/Path C/paid packs decode on demand. Avoid wake-ups solely to recompress. Eng picks codec in `[MS-FINE-TELEMETRY]` / `[MS-AMBIENT-CAPTURE]`.
3. **Ambient on-ramp (default Path L):** While Path H runs, smart-select candidates for coverage (trigger snapshots, hard/uncertain cases, underrepresented contexts, periodic negatives) — not a full-drive dump. Cap queue; drop near-duplicates.
4. **Semi-automated labeling:** Propose labels on trigger; **positive/rare classes require cheap human confirm/reject** (notification or end-of-drive review) so Path H errors are not cloned into the “model.” Abundant negatives may auto-label with audit sampling. Personalized freeform `labelSchema` is enough for v1; standard templates later.
5. **Diversity & split gates:** Before `trainable` / `trusted`: per-label minima and balance, held-out split never used for fitting, diversity checks (not hundreds of labels from one short stretch). Studio health strip surfaces counts + holdout + diversity warnings.
6. **Maturity states:** `none` → `collecting` → `trainable` → `candidate` (trained, not trusted) → `trusted` (user-promotable; demotable anytime). Signals: volume/balance, holdout score, live confirm/reject rate, fallback/override rate, diversity health.
7. **Deferred train / test prompts:** When gates say ready — notify and/or opt-in opportunistic train (charging + idle / “train at night”; never surprise heavy CPU on a hot phone). User opens Model Studio (phone or laptop Chrome on local edge) → review → **Train on phone** or **Train on laptop** → bind → prompt to **test learned mode**. Heuristic remains fallback until `trusted`.
8. **Studio surfaces:** Timeline/charts with fine overlays, map, smart candidate rail, label controls, dataset/drive picker, health strip, train actions, post-train test/keep-heuristic.
9. **Exemplar:** Pothole-style Bro Code = Path H then ambient Path L. Tweet/X chaining stays deferred under `[MS-XTER-AGENT]` / `[MS-AGENT-CHAINING]`.

### 2.10 Bro Code Commons & Simple Licenses (Arch v3.10)
Future-scope ecosystem loop so User A can publish Bro Code to a shared place, User B can pick it up, modify it, and share it again — under author-chosen **simple licenses**. Transport/registry Eng is deferred (`[MS-BROCODE-COMMONS]`); Arch freezes bundle, license, and fork rules. The “common place” is a future **Bro Code Commons registry** that extends the C4 marketplace pool (§2.7). Peer-to-peer URL exchange may come later.

1. **Publish → pickup → modify → re-share:** Author publishes a Bro Code bundle to the commons with a license. Another user acquires/picks it up into their vault at **C4**, may IMPROVE/modify, then may publish a new revision (re-share) subject to license rules.
2. **Simple licenses** (author sets at publish; immutable for that revision):
    * **`remix_free`:** Modify and re-share **without** required reference to the original (no mandatory attribution / lineage link in the commons index).
    * **`lineage_indexed`:** Modify and re-share allowed, but the new publication **must** register as a child in a **modification index** (fork graph: `parentRevisionId`, modifier, timestamp). Forks under this license remain discoverable from the lineage root.
    * **`paid`:** Acquisition/use/redistribution requires payment terms (amount/currency/channel are product/Eng later). Paid gate is **acquire** only — pickup still lands at C4; due diligence is never skipped.
3. **License conflict rules:** If parent is `lineage_indexed`, a child publish **must** keep lineage linkage (may not re-license as `remix_free` to erase ancestry). If parent is `remix_free`, child may choose any of the three. If parent is `paid`, re-share follows the paid grant (default: re-share only if the grant allows; otherwise private vault only). Exact paid TOS deferred; Arch freezes `paid` as a first-class license class.
4. **Published bundle metadata (illustrative):** `license`, `revisionId`, optional `parentRevisionId`, author id, Bro Code source + schema. Bound models and labeled packs are **opt-in attachments** with separate consent — never auto-included (§2.6).
5. **Commons ≠ data market:** Bro Code source licensing is distinct from `[MS-DATA-MARKET]` labeled-pack sale. Near-term local marketplace UI (`[MS-USER-ECOSYSTEM-UX3]` / `[MS-USER-ECOSYSTEM-AGT2]`) is the client shell; commons + licenses are the later extension.

## 3. ENGINEERING & TOOLCHAIN CONSTRAINTS (Eng v2.8 Frozen)
* **Framework:** Flutter (Native background channels, cross-platform UI, Riverpod state).
* **Audio Toolchain:** Pure `record` for raw M4A capture, `audioplayers` for playing LLM-generated responses.
* **Agnostic BYOK Engine:** Multi-model support stored in local `SharedPreferences`. Abstracts API variance (Base64 inline data for Gemini vs Whisper APIs for OpenAI) into a single logical pipeline.
* **Local Web Stack:** Background HTTP server (Shelf) hosting HTML5 dashboards served locally at `http://localhost:<port>`.
* **JS Runtime:** QuickJS embedded sandbox for dynamic local script execution.
* **Testing & Simulation:** Contains a built-in "Silent Dialogue Simulator" allowing text-based prompt execution, bypassing audio for developer testing.
* **UI Architecture:** 3-Page horizontal swipe architecture (`PageView`), strictly separating Settings, Command Center, and a 4-Tier Security Matrix Agent catalog.

## 6. PHYSICAL TESTING PROTOCOLS & QA CASES
To guarantee extreme robustness of the native edge runtime before compiling further agents, execute these physical/desktop integration tests:

### Test Case A: The Sovereign Vault Integrity Check (`[MS-VAULT-SERVER-ENG1]`)
*   **SOP:** Open the app and let it run for 15 seconds.
*   **Validation:** Verify that mock telemetry records (Z-accel, lat, lon) are successfully logging into the background SQLite database by verifying no query errors appear on the console or Log panel.

### Test Case B: Edge Server Health (`[MS-VAULT-SERVER-ENG2]`)
*   **SOP:** From your laptop (or on Chrome inside your mobile), navigate to `http://localhost:8080/api/status`.
*   **Validation:** Browser must instantly return a structured JSON response verifying the server's `"status": "active"`.

### Test Case D: Javascript Agent Sandbox (`[MS-JS-BRIDGE-ENG1]`)
*   **SOP:** Launch the app (use Git Bash: `flutter run`). In the Command Center text simulator, type: `Run telemetry counter` or `Count telemetry records`.
*   **Validation:**
    1. Log panel shows **"Executing Javascript Agent: TelemetryCounter..."** followed by **JS Bridge** step logs (`System.querySQL`, etc.).
    2. TTS speaks a summary including the telemetry row count.
    3. Agents drawer lists **TelemetryCounter** alongside Calculator and DrivingCoach.

### Test Case E: LLM Agent Authoring + Dashboard (`[MS-USER-ECOSYSTEM-ENG1]`, `[MS-TELEMETRY-DASHBOARD]`)
*   **SOP (Path A — AI authoring):** Save a valid BYOK key in Settings. Go to Agents page → CREATE AGENT → AI AUTHORING. Type: *"Build a live telemetry dashboard charting accelerometer Z over time from the local vault."* → GENERATE WITH AI. Review the generated name/description/JS → SAVE & REGISTER.
*   **SOP (Path B — manual import):** Agents page → CREATE AGENT → MANUAL IMPORT. Name `TelemetryDashboard`, paste `examples/TelemetryDashboard.js`, choose a security class → SAVE & REGISTER.
*   **Validation:**
    1. New agent card appears under its security-class tab; tapping it shows description, schema, and JS source.
    2. Tap RUN — the Command Center / execution shows JS Bridge steps; the agent writes an HTML asset to the vault.
    3. Agents page → VAULT DASHBOARDS lists `telemetry_dashboard.html` with a same-origin URL; OPEN renders a live-refreshing accelerometer chart in the browser.
    4. Voice/text: *"Run telemetry dashboard"* re-executes the vault-stored JS agent (LLM router discovery).
    5. DELETE removes the agent from both the vault and the live ecosystem.

### Test Case F: Verb-Intent Dispatch + Core JS Calculator (`[MS-CORE-INTENT]`, `[MS-CORE-JS-MIGRATION]`)
*   **SOP:** Launch the app on a physical device (use Git Bash: `flutter run`). In the Command Center text simulator (or by voice):

## 7. ARCHITECTURE & ENGINEERING HISTORY (Changelog)
* **Arch v3.10 / Eng v2.8 (Current):**
  * *Paradigm:* **Bro Code Commons & simple licenses** (§2.10) — publish → pickup (C4) → modify → re-share under `remix_free` / `lineage_indexed` / `paid`; license conflict rules; commons registry as shared place.
  * *Marketplace (§2.7):* Listings are Bro Code units with `license` + `revisionId` (+ optional parent); paid acquire ≠ skip due diligence.
  * *Sovereignty (§2.6):* Commons publish is user-authorized egress of authored code (not auto models/labels); distinct from `[MS-DATA-MARKET]`.
  * *Milestones:* `[MS-BROCODE-COMMONS]` designed (deferred); `[MS-USER-ECOSYSTEM-UX3]` / `AGT2` cross-linked as near-term shell. **No Eng bump.**

* **Arch v3.9 / Eng v2.8 (Legacy):**
  * *Paradigm:* Alternative 3 rewritten as **sovereign data + dual-locus ML** (§2.2): Path H heuristic ships first; Path L learned binding matures via ambient capture → labels → train (phone tiny and/or Path C laptop/GPU) → bind → test; inference always on-device.
  * *Model Studio (§2.9):* Class 1 Label/Train Studio; coarse vs fine telemetry; **mandatory write-time compression** + retention for fine candidates; smart candidate selection; semi-auto labeling (human confirm for positives); diversity/holdout gates; maturity states; deferred train/test prompts; IMPROVE must not silently unbound models.
  * *Bridge:* `System.runModel` / `System.runONNX`; AUTHOR optional learned-path slots (`usesModel`, `labelSchema`, `capturePolicy`, `splitPolicy`, train locus).
  * *Sovereignty (§2.6):* Model Studio self-use train/export/import and later labeled-pack sale are explicit exceptions; casual raw dump button still forbidden; ambient collection is not egress.
  * *Milestones:* `[MS-MODEL-STUDIO]` ladder designed (queued); `[MS-ONNX-NATIVE]` superseded; `[MS-DATA-MARKET]` extended for labeled packs. **No Eng bump** — implementation not started this freeze.

* **Arch v3.8 / Eng v2.8 (Legacy):**
  * *Terminology:* User scripts are **Bro Code** (Bhai log). **Agent** means internal Coder / Tester / Deployer workers.
  * *Agentic IMPROVE (`[MS-BROCODE-AGENT]`):* Tool-loop coding agent (`apply_edit` / `sandbox_run` / …), host reject-done, live AGENT ACTIVITY + model-wait heartbeats, Est. context circle; APPLY only when verified.
  * *Coder Agent:* IMPROVE / refine prefers full `scriptBase64` rewrite; surgical Base64 patches are fallback only.
  * *Sandbox vault:* In-memory SQLite for C4 smoke tests via `TEST IN SANDBOX` and Tester Agent — never sovereign vault.
  * *Types:* `BroCode` / `BroCodeService` with typedefs for `AurBhaiAgent` / `AgentService` during migration.

* **Arch v3.7 / Eng v2.7 (Legacy):**
  * *Paradigm:* Single-Call Elicitation Protocol (§2.8). One LLM call per turn fuses intent classification + App Spec template fill + spoken confirmation. Eliminates 3–4 chained round trips that caused ~5s authoring latency.
  * *App Spec:* 13 conditional slots with implicit-consent lifecycle (empty → proposed → confirmed); **mandatory final BUILD gate** (review phase) replaces auto-build-on-silence; concise per-turn echo; visual authoring panel.
  * *Intent safety net:* Deterministic AUTHOR reclassification when the LLM returns DIRECT for "build/make/create … agent/app/dashboard".
  * *Execution gate (§2.7):* RUN disabled for C4/C3 in UI and JS adapter; enabled only at C1/C2 after promotion (or force-promote with `FlutterFragmentActivity` + `local_auth`). No sandbox-trial execution of unverified agents.
  * *Dashboard UX:* OPEN DASHBOARD only for HTML keys written in the current run; run errors styled distinctly; due-diligence scan strips embedded dashboard HTML templates to avoid DOM/fetch false positives.
  * *Refine UI:* Agents page IMPROVE sheet with contextual chips from run errors and scan findings; build date/time on agent cards.
  * *IMPROVE verify-before-handoff:* Surgical Base64 edits + local SyntaxError fix + capped multi-turn repair; QuickJS syntax must pass before APPLY. Due diligence clarified as static scan ≠ RUN (§2.7); follow-on `[MS-DUE-DILIGENCE]` for false-positive / UX hardening (Locator-class DOM + SyntaxError coexistence).
  * *English only:* Removed hi-IN default and multilingual prompt branching until re-enabled.
  * *External integrations:* Slot 13 captures X/FB/Instagram/YouTube/Threads/webhook actions; BYOK platform keys in Settings; C2 egress gate per §2.6/§2.7.
  * *Performance:* Default Gemini model `gemini-2.0-flash`; removed hardcoded 1500ms wake delay after custom response playback.
  * *Implementation:* `[MS-CONV-AUTHOR]` + in-UI `[MS-AGENT-REFINE]` + `[MS-USER-ECOSYSTEM-ENG3/ENG4]` — In Review pending on-device test.

* **Arch v3.6 / Eng v2.6 (Legacy):**
  * *Paradigm:* Introduced the Conversational Agent Authoring & Refinement framework (§2.8). The Core becomes a verb-first LLM intent dispatcher (EXECUTE / FEED / AUTHOR / REFINE) with multi-turn session state.
  * *Authoring:* One-shot and Socratic (slot-filling) dialogues converge on a single spec engine terminated by "proceed", producing a Not Verified (C4) JS agent.
  * *Refinement:* "Fix <agent>" patches an existing agent's source conversationally with versioning; a material change resets the tier to C4 per §2.7. Motivating case: teaching `CalculatorAgent` the `^` power operator.
  * *Core-as-JS:* Core agents (Calculator, DrivingCoach) migrate to refinable JS vault agents so the whole ecosystem is user-improvable; native Dart is reserved for Class 1 hardware shells only.
  * *Milestone Additions:* `[MS-CORE-INTENT]`, `[MS-CONV-AUTHOR]`, `[MS-AGENT-REFINE]`, `[MS-CORE-JS-MIGRATION]`, `[MS-AGENT-FEED]`, `[MS-LLM-AGNOSTIC]`.
  * *Implementation (Eng v2.5):* Landed `[MS-CORE-INTENT]` — `LlmParsedResponse` now carries `{intent, targetAgent, payload}`, classification is fused into both the text and Gemini-audio parse calls, and `VoiceHandshakeEngine` routes on a single `_dispatchIntent` table (AUTHOR / REFINE / FEED are stub hooks pending their milestones). Landed `[MS-CORE-JS-MIGRATION]` — Calculator (now with the `^` power operator) and DrivingCoach are seeded into the sovereign vault as C2 JS agents via `seedCoreAgentsIfMissing`; native Dart registrations removed from `agentServiceProvider` (classes retained unregistered for rollback). Resolved the `[MS-USER-ECOSYSTEM-UX2]` / `[MS-CONV-AUTHOR-UX1]` overlap (former superseded). Both milestones In Review pending on-device QuickJS validation (Test Case F).

  * *Constraint:* Used standard `flutter_tts` for robotic voice responses.
  * *Deprecation Reason:* Native OS dictation struggled massively with non-English dialects.
